# Orchestration Execution State & Run Control\n\n## Run State Model\n\n- PENDING: run registered but not started.\n- RUNNING: an eligible stage is executing.\n- SUCCEEDED: all required stages completed successfully.\n- FAILED: a stage failed and requires deterministic investigation or retry.\n- BLOCKED: execution cannot continue because an upstream gate failed.\n- RETRYING: a permitted retry is being prepared.\n\n## State Transition Rules\n\nPENDING -> RUNNING -> SUCCEEDED\nPENDING -> BLOCKED\nRUNNING -> FAILED -> RETRYING -> RUNNING\nRUNNING -> RETRYING -> RUNNING\nFAILED -> BLOCKED when deterministic recovery conditions are not satisfied.\n\nTerminal states are SUCCEEDED and BLOCKED.\n\n## Run-Level Control Fields\n\nRun identity, pipeline version, timestamps, overall status, current stage, checkpoint position, attempt number, failure reason, and creator identity must be recorded.\n\n## Stage-Level Control Fields\n\nEach stage records its status, attempt number, timestamps, failure reason, and checkpoint position before and after execution.\n\n## Checkpoint Rule\n\nCheckpoint advancement is permitted only after successful processing. A failed stage must not advance the authoritative checkpoint.\n\n## Retry Rule\n\nRetry is allowed only for an identified retryable failure. Retrying must preserve deterministic checkpoint and idempotency controls.\n\n## Blocking Rule\n\nA failed blocking stage prevents dependent downstream stages from executing.\n\n## Auditability\n\nEvery run and stage transition must be traceable by run ID, stage ID, attempt number, and timestamps.\n\n## Production Safety\n\nRun control must not bypass CDC, checkpoint, DQ, reconciliation, schema, security, or governance controls.\n\n## AWS Boundary\n\nThis state model is the logical local control-plane design. AWS orchestration execution is not claimed.
